# v0.17.0-r1 料理停滞修复

基线：完整 v0.17.0。官方规则参考构建：756039。仅修复料理调度、动作清理、日志和取消候选；不新增玩法，不重写材料、建筑、友谊容器、通信或自我维持系统。

## 已确认原因与证据边界

1. Hub 的20秒动作超时分支原来只标记受阻，没有通知玩家，也没有统一释放锅、预留与监听。
2. ActionBusy 在创建 inflight 前直接返回，准备阶段没有进展监测；反复因锅内容变化或材料变化重规划也可能没有结束边界。
3. 停止动作会同步触发失败回调。原超时、暂停、取消未统一先清除 inflight/提升 attempt，可能将旧失败当作新结果更新。
4. 料理没有旧工作 job；取消/暂停时 t.job 和 core.job 同为 nil，却满足相等判断，提前调用旧工作系统停止。新增同步失败测试复现并修复此清理顺序问题。
5. Select 已排除 completed/cancelled。不能说已结束记录原来参与取消；真正的代码缺口是未指定取消范围时所有未结束项（包括旧受阻项）一起造成歧义。现在唯一执行中/等待原版烹饪的任务优先；仍有多个合理候选则列出中文名称、状态、编号确认。单项取消不取消其他任务；全部取消仅作用于未结束项。

现有旧日志没有后续任务进入搜索、动作实际执行、库存变化的证据。本次没有对应的新游戏日志，不能确认授权冰箱后那次停滞究竟发生在哪一环节。未授权冰箱导致缺料不是缺陷。

## 修复行为

- 统一 Block / Invalidate：先使动作与回调失效、清除 inflight，再停止本料理持有的动作；释放材料预留、锅占用和事件监听。不会强制打断别的任务、补给或不可中断状态。保留真实已取材料、锅内材料、已开锅批次和已收取/交付数量，不重做已消耗批次。
- 单动作仍为20秒；准备阶段30秒没有真实动作进展受阻，准备前连续忙碌20秒受阻。不是延长超时。正常短暂忙碌允许等待；真正已启动的原版烹饪等待不计入准备停滞。
- 连续三次动作失败、材料预留失败或无进展重规划有明确反馈。恢复会重新开启本轮准备预算和校验；不抹除实际进度。执行器异常也通过统一入口报告。
- 取料和放料都检查物品仍属于实际来源，使用真实 RemoveItem/GiveItem；核对双方数量差，继续遵守授权、范围、容量、接收条件和原版锅状态。
- YBF_COOK_TASK 仍通过 locomotor.PushAction → 原版 wilson/wilson_client doshortaction → Perform → 成败回调执行。注册正确并不证明游戏寻路/状态图到达 Perform，新增日志用于辨认断点。
- “任务终止”可直接进入现有任务控制；只取消唯一当前任务，旧完成/取消记录不参与，旧受阻记录不会挤掉唯一正在执行项。

## 诊断读取

服务器日志前缀 `[YBF COOK FLOW]`，用 task=稳定任务编号关联：scheduler / action_busy / search_start / search_yield / search_end / reservation_failed / replan / submit / perform / actual_result / action_success / action_failed / action_timeout / pot_check / blocked / executor_error。

日志记录缓冲动作ID、状态图名、busy/working/prechop/premine/nointerrupt标签、补给pending、可用食材（最多40种）、步骤、目标GUID、距离、双方实际库存前后数量、锅槽位与真实烹饪/完成状态。相同阶段和摘要最多每10秒一次，状态变化立即记录；每次真实动作提交/结果单独记录。不记录模型密钥、不逐帧输出。

没有 search_start：查看 scheduler/action_busy。有 submit 没有 perform：未到实际动作执行，查缓冲动作、路径和状态图。有 perform：看 actual_result 的库存变化及失败原因。原版开锅后看 pot_check，不能凭时间认定完成。错误原因暂不明时保留 no_verified_inventory_change 等日志诊断，不冒称确认具体路径问题。

## 验证结果

- 82项相关 Python 检查通过。
- 46项料理/任务 Lua 检查通过（包括本轮7项针对性模拟）。授权冰箱中蛙腿、胡萝卜、浆果、冰完成真实组件接口取材、放料、原版 Stewer 开锅、等待、收取及交付计数。
- 覆盖同步 StopAction 失败回调、过期回调、20秒超时、长期 busy 不强制打断、三次动作失败、三次重规划、释放预留/锅监听、独立树枝任务继续，以及完成/取消历史不干扰当前取消。
- 原有22种输入经过真实 HTTP 服务/生产解码及游戏聊天入口；新增“任务终止”经过游戏聊天入口本地控制。模型提供者为固定模拟响应，不是真实模型调用。
- 建筑48项、基础46项、Lua语法26项及原0.16语言回归通过。各 runner 中 PASS 包含不同粒度断言，不合并当作统一测试数量。
- 游戏实体、寻路、状态图运行由模拟环境提供；官方烹饪规则与 Stewer 为提供源码。真实游戏验证、真实外部模型调用：本轮未运行。模拟不能证明游戏状态图、寻路均已正常。

## 最少游戏验收

1. 替换模组和外部程序，保留自己的密钥，重启程序与服务器，双方版本应为0.17.0-r1。附近放空闲锅；给冰箱赋予友谊，放蛙腿、胡萝卜、浆果、冰各一份。
2. 说“用冰箱里的材料做一份蛙腿三明治给我”。核实冰箱减少4份、锅实际开始、实际产物入包并交付1份。过程不要求打开容器动画。
3. 料理等待期间安排“给我一根树枝”，核实其他任务可继续。保留旧完成记录，再启动新的料理，说“任务终止”；只取消当前唯一执行项，已开锅原版加工不停止、不重做。
4. 让材料途中被取走或路径受阻，确认在有限失败/20秒动作期限内收到具体阶段受阻反馈，库存和锅材料不消失。恢复后重新核实条件。
5. 若仍“稍微移动后停止”，提供此次 server_log.txt（同一 task 从 scheduler 到 blocked 的区段）及 client_log.txt；重点看是否到达 submit / perform。不能仅凭提示文字判定成功。
