# my_best_friend v0.17.0 更新、范围与交接

基线：已交付并由玩家确认 0.16 系列游戏测试完成的 v0.16.0-r6。保留现有材料获取、递归制作、三种建筑定位、友谊容器、通信与自我维持执行器。本次新增烹饪执行器和有界任务台账，未增加主动行为、农业、晾晒、设施建设或蓝图。

## 审计结论与实现

原工作引擎已有真实库存/动作记账、友谊容器权限、材料预留、暂停恢复及建筑预制；原通信已回传最终回答。缺口是工作引擎只有一个当前任务、没有锅批次与等待状态，知识确认不等于可执行提议，原模型协议只返回一个顶层动作。

现在台账保存最多 8 项未结束任务、32 项历史，稳定编号绑定持有人和朋友；获取/制作/建筑仍交给原工作引擎。烹饪用原版 COOK、HARVEST 和四槽真实容器流程；等待由锅的真实状态、批次标识、完成事件和每 2 秒检查决定，不用预计时间认定成功。等待锅释放执行机会，收取不无条件打断正在进行的原任务。材料预留协调朋友，不锁玩家。新任务加入队列，不用聊天记忆覆盖等待任务。

## 来源、规则与实际执行范围

复用此前上传并校验的官方构建 **756039** 脚本、本地化和身份知识。`knowledge/cooking_rules_756039.json` 保存 81 条基础/非食物判定及出处、行号、SHA256；`tests/official_cooking_756039` 保存直接对照的官方代码。运行时读取当前游戏 `cooking` 的食材标签、配方优先级、权重、产量和原版判定，不靠固定材料组合或模型记忆。

在 756039 对照环境中，普通锅 70 条、便携锅 81 条（均含 2 条非食物规则）；食物基础规则分别为 68、79 条。加上档案锅重复注册和 316 条调味变体，共 537 条“锅具—规则”索引。**这些是规则数量，不是已实测能做的菜数或任务完成率。** 全部基础谓词已收录，但没有逐一完成 79 种食物的游戏制作测试。

执行器支持已部署的普通烹饪锅、便携烹饪锅，不要求新增友谊锅。遵守当前锅的接收规则、占用状态和原版启动判定。便携专用料理按对应锅的实际配方表选锅；不部署便携锅，不绕过部署或制作资格。档案锅、调味站/调味变体、非食物锅产物、营火单份烤制、晾肉架、种子袋和模组自定义食谱不执行。锅的配方表若含未核验的新增或替换谓词，无法保证原版选菜结果，本轮不开锅；不调用其回调试探。若第三方替换了官方谓词，来源不再属于官方模块同目录，则不把其回调当知识读取执行。

四槽组合只进行无副作用的官方 `test(cooker,names,tags)` 判定。保留所有最高优先级竞争产物及权重；指定菜只使用唯一胜出的可靠组合，有随机竞争而没有另一可靠组合时不承诺产物。按实际库存枚举，可为不同批次采用不同有效组合；每轮最多 40 种食材、40000 个组合，跨批次最多 1024 个候选和 20000 次有界分配检查。预算不足会明确说明，不能据此断言没有配方。稀缺性采用标签/数量的保守代价；不是全局最优算法。

自由选择默认一份、一锅，按较低新鲜度、已有锅料、数量和稀缺标签排序，不因模糊需求耗尽仓库。荤含配料中的肉、鱼、蛋、乳标签；素不含这四类。植物肉遵循原版肉标签，这不是纯素饮食承诺。选择时检查接收者原版 eater 条件；自定义食性、特殊增益与完整角色饮食机制不承诺全覆盖。

食材只来自朋友库存、范围内友谊容器及正在处理的空闲锅已有材料；不取玩家背包，不补采食材。仓库限定来源有逐单位取材记录，原有同名自带材料不会被冒用。默认任务区域半径沿用 32，不扫描世界或跨分片。只用仓库材料时，锅原有材料先保存回库存，不把它冒充仓库取材。锅已有产物先真实取出妥善存放，不算新料理数量；已有材料可参与配料，不匹配材料先真实取回，不销毁清空。任一取放、开锅、收取前再次校验槽位、数量、权限和批次。

未指定去向优先可接收的友谊冰箱，再沿用其他友谊容器、玩家、安全地面的回退。指定给玩家则优先交付；指定容器只在授权范围内选择。真实入包与真实转移数量决定完成，原版一锅产出多份按实际数量报告。交付中产物受任务保护；明确保留在朋友库存的完成产物也受保护，后续自动补状态与烹饪不擅自使用。玩家从冰箱取走物品不会因此授予朋友自动取食权限。

## 多轮提议与任务操作

“我饿了”创建结构化待确认提议；“要／好／好呀／做吧”接受当前提议并重新核实条件。提议创建不取材、不预留、不启动锅。拒绝、数量/类别/去向修改、询问方案分别处理；询问方案/修改可刷新有效期，无关闲聊不刷新。默认 60 秒，可在模组配置选择 30/60/90 秒，不催促。关闭聊天窗口不丢失有效提议。

新任务默认撤销旧提议；同句刚接受的提议保留。重复接受、失效确认、延迟旧回复不能再创建或执行一次旧任务。每位玩家和每位朋友隔离；模型的 proposal_id 必须与发送时绑定的本地提议一致。

一句话最多 6 项操作：新增获取/制作/建筑或烹饪、提议接受/拒绝/修改、指定任务取消/暂停/恢复/修改、状态查询。例：“别做饭了，拿一根树枝给我，再继续刚才的建筑。”按顺序处理独立项，指定依赖只有前项任务实际完成后推进。多个同类任务不能凭“别做饭了”猜选其中一个，要说明编号/名称；只有“全部取消”作用所有任务。

查“当前都有哪些任务”可见编号、名称、状态、数量、去向和阻碍。状态区分待确认、待执行、执行中、等待烹饪、受阻、暂停、完成、取消。给定任务编号可单项控制。已有多目标获取/制作任务内的目标修改仍调用原修改接口。正在锅里加工的料理取消只停止自动收取/交付；原版加工继续，已消耗材料不能撤销。暂停也不停止原版计时。

## 保存与恢复

持久化已接受台账、目标、进度、材料来源记录、建筑位置/预制信息及锅持久化身份/批次；不保存回调、搜索协程或短期倒计时。读档后重新核实本分片范围内原锅、原产物和建筑完成记录。原锅失踪、产物被取走/腐败、批次变更时受阻并报告，不自动另做一锅或重复建造。持有人离开时保留任务，重新上线后可按编号恢复。

未接受提议在完整读档后失效，孤立“要”必须重新说明。旧版本升级不会凭历史聊天重建工作。接受任务的普通 goal 可恢复；早期非 goal 的旧计划没有足够结构化信息时会受阻，不能假称已无损恢复。没有迁移旧版正在进行的短期提议。

## 延迟、诊断与剩余边界

沿用每句话一次模型调用，没有增加配料求解的模型轮次；本地事实校验和组合搜索负责配料。模型输入只增加有界任务/提议与相关烹饪条目、食材摘要，不发送整套食谱。复杂库存组合采用协程分片求解；原版锅等待是实际加工时间。日志含任务编号、锅批次、开始/受阻原因和原有通信链，不记录密钥。

料理任务尚不提供全局最优材料调度、复杂优先级或多朋友自动分工。满背包无法接收锅产物时保留锅并受阻，不随意丢装备腾空间。有限搜索未找到可靠组合、特殊食性、模组改写规则、设施远离/被占用等都可能阻碍任务。料理规则收录不等于库存可行或执行成功。既有全面百科仍保留原覆盖边界，本轮不宣称全面知识已完成。

## 验证结果与精简游戏验收

自动与模拟验证记录在 `tests/v0170_*.log` 和 `knowledge/cooking_validation_756039.json`：82 项 Python 检查、22 种自然语言经真实 HTTP 解码与游戏聊天入口模拟；官方食材身份 155 项，6 组配料共 240 次原版随机判定对照。完整模拟做出的未见样本为蛙腿三明治、火龙果派、蓝带鱼排、彩虹糖豆；另验证“肉汤”简称进入炖肉汤完整流程。Python 协议/知识/桥接回归、Lua 语法、原制作/容器/建筑/地皮定位回归、官方烹饪谓词和原版 stewer/动作正文、真实 HTTP 解码到真实游戏聊天入口的模拟通过。模型提供器、世界、路径、状态图和引擎对象由夹具模拟。**本轮未调用真实模型，未运行 DST 游戏；不能写成游戏实测通过。**

更新时同时替换 `my_best_friend` 和 `external`，保留自己原有密钥配置文件，不从包内覆盖密钥。所有客户端和服务器使用同版本，重启后台与服务器；建议备份存档后用测试世界。

1. 放一个现有普通锅，给朋友/友谊容器放蛙腿、胡萝卜、浆果、冰各一份，说“给我做一份蛙腿三明治”。核实四槽、真正开锅、产物实际入包与交付，而非只看回复。
2. 用火龙果、胡萝卜两份、树枝一份说“来份素菜，弄好拿给我”；核实火龙果派。用已部署便携锅与蛙腿两份、鱼、浆果测试蓝带鱼排，附近有普通锅也应选择适用锅。
3. “我饿了”后检查没有取材；“要”才安排。重复“要”、拒绝、等 61 秒后“要”、无关闲聊、改为两份再确认分别验收。材料只在普通箱时不得使用；“只用友谊箱里的”不能消耗朋友原有同名材料。
4. 在做饭等待中说“给我一根树枝”，应先完成取材/交付，锅完成后再收取。说“别做饭了，拿一根树枝给我”只取消对应烹饪；多个同类任务应澄清。按清单编号测试暂停、恢复、修改数量、单项取消及全部取消。
5. 开锅后玩家提前取产物、拆锅或取消任务：不得重复计数、自动重做或假称原版加工被撤销。两位朋友争用同一食材、玩家途中取走材料时核实实物不复制、数量不足明确反馈。
6. 友谊冰箱满、玩家满、原版一锅彩虹糖豆产出三份时，核实部分存入与地面回退，装备不被丢弃。彩虹糖豆指定配料可用蜂王浆、胡萝卜两份、浆果；宽泛吃饭不会优先选零饥饿料理。
7. 等待开锅后保存重载：原锅原批次只收一次；不把未接受提议恢复。查询知识不启动动作；再做一次非建筑制作、友谊容器存取及固定点/脚下地皮建筑回归。

游戏验收请保留 server_log、client_log、后台日志以及锅/朋友/容器实际库存变化；若有失败，以具体状态与批次定位，不将所有失败归咎模型。
