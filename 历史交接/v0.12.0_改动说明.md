# v0.12.0：目标驱动的有界依赖补齐

基线为当前用户上传的 v0.11.0 完整包，和前次交付包字节一致。本次增量复用原工作组件、库存、动作护卫、连续砍挖窗口、拾取、真实制作/给予、打断、跟随等待和补状态逻辑；没有整体移植参考模组，没有新增并行工作控制器。

## 两个问题分别处理

### A. 指令解析/下发失败

新旧后台截图都显示 `MODEL_ERROR ... type=ValueError http=none`，随后 `TASK_END state=error`。旧 v0.11.0 把模型响应为空、超长和意图/动作/字段/步骤校验等显式 ValueError 都压缩为同一句日志；JSON语法错误通常是 JSONDecodeError，而截图没有该类型。截图没有模型原文或具体校验信息，因此**无法追溯确认当时是哪一个字段失败**，也不能据此认定复杂目标不支持，或认定是 HTTP/密钥失败。

另一个独立发现：截图实际游戏快照为 `work.radius=12`，没有新增工作版本字段；已交付 v0.11.0 源码的半径下限为32。这提示运行中的游戏代码与提供包存在不一致，可能仍加载旧副本或未重启。不能仅凭截图判断具体部署原因，也不将所有 ValueError 归因于此。

新增 `external/decision.py` 负责严格结构校验。日志和任务错误包含：

- `category`：decision_json、decision_schema、provider_json、provider_envelope、network、internal。
- `code`：如 invalid_json、invalid_quantity、invalid_target_fields、inconsistent_action、missing_content、model_steps_forbidden。
- `path`：已知字段路径，例如 `$.quantity`、`$.item[0]`。
- `reason`：具体校验规则，而不是只打印异常类名。
- `structure`：已知字段类型、缺失字段、条目数、未知字段数、JSON行列、处理阶段等。不会包含模型原文、未知字段名或值、异常原始字符串、HTTP响应正文及密钥。

提供商响应外层和模型内部 JSON 分别检查。合法目标统一归一化为 `{targets=[{item,quantity}],deliver}` 才下发；模型生成的采集/科技/制作步骤不接受，原仅砍树按棵的直接动作除外。旧 Request/RequestPlan 本地接口仍保留供兼容及特殊直接动作使用。

没有自动格式修复或自动重发模型请求（修复次数为0），避免把失败重试变成重复执行。请求ID/消息tag、任务令牌与动作尝试编号仍去重，过期或被取消结果不得执行。

聊天分别显示“指令解析失败”（未下发工作）和“游戏执行受阻”（目标已接受但条件不足）；网络/提供商连接失败仍为连接类提示。ACCEPT新增后台/游戏版本用于定位运行副本。

### B. 工具材料依赖补齐不完整

新增 `scripts/ybf_goal_planner.lua`。AI只确定目标物品、数量和交付要求；本地解析器在每次动作前重新根据真实库存、配方、可用工具、解锁和科技生成**下一步动作**，不是从模型接收固定步骤。

统一流程：检查真实库存与剩余目标 → 优先选择地面成品/所需资源 → 缺少采集工具时递归补齐工具材料 → 真实制作/装备工具 → 执行采摘/砍挖/拾取 → 核实实际库存和工作结果 → 重算缺口 → 适用科技/真实制作 → 返回真实交付。

工具只是通用资源动作的前置条件；没有 cutstone 专用自动化脚本。所有配方从 GetValidRecipe/AllRecipes 和 builder 的真实数据读取，包括材料折扣、产出量、角色限制、科技、解锁、原生材料选择和真实 BUILD 成本。已有成品跳过材料/科技；已解锁配方无需寻找科技站。材料不从开放箱子取；拒绝免费或预付材料制作路径。

循环检测沿当前依赖路径进行。例如只有矿内燧石、但没镐也没有足量先行燧石，明确报告循环依赖，保留已得材料。配方中不在当前自动获取范围的材料报告该材料不可获取，而不是“无法处理”。深度/节点/动作/工具/恢复/时间和逐目标重试均有上限，具体数值见开始这里。

进度以真实持有量和经过收发库存核验的已交付量计算；工具消耗导致父任务材料下降会重新补缺。倒树/敲矿只证明工作进展，必须拾取实际掉落才增加目标库存。多种资源只计对应目标，附带物资正常保留，额外产出不全部交付。

受阻任务保留在当前会话，报告已持有、已交付、成品缺口、前置缺口及当前阶段。`RequestGoal`、`Status`、`ResumeGoal`、`Cancel` 可供后续规划系统调用。Resume先重新验证库存/条件并更换回调令牌；结果无法核验时禁止自动恢复，以免重复制作/给予。

同一时间仍由原 Core 的一个工作任务控制动作，子目标不另开后台任务。补状态复用原逻辑，在动作之间暂停并保留进度，恢复后重新检查条件。受阻释放工作控制；原等待模式保持等待安排，不恢复跟随/瞬移。停止或新合法目标废除旧动作/任务令牌；聊天中的精确“停止任务/停止工作”直接本地停止，取消同一朋友等待中的模型请求，不依赖模型成功。

## 范围与参考取舍

默认朋友自身半径32世界单位，配置可为32/40/48/64；目标同时受任务起点同半径约束。沿用现有有限本地扫描，不使用玩家视野或领队坐标，不跨洞穴或无限外扩。

自动获取六种基础资源及六个基础配方：树枝、草、木头、石头、燧石、金块；斧头、鹤嘴锄、石砖、木板、绳子、火把。可拾取范围内已有基础成品和工具；其他目标已有库存足够时可交付，缺少时明确报告当前不能获取。暂不扩展所有食物/高级材料规划、战斗备料、取箱子或建科技站。

参考 My Mate 的目标/工具选择、动作完成再继续、库存装备与制作队列思路；GrimWorld 的任务释放及失败边界。保留当前原生 BufferedAction/SG/库存与 builder 核验方案，没有复制领队搜索、全资源上交、临时生成工具或免费制作机制。

## 验证结果与边界

| 层级 | 本次结果 | 能证明什么 |
|---|---|---|
| Lua静态/模拟世界 | 通过 | 原动作适配器、空背包两条依赖链、材料成本/产出/解锁、真实库存计数、阻塞恢复、循环、数量交付、停止/替换及补状态暂停；世界、导航和 builder 为模拟 |
| 聊天服务器入口模拟 | 通过 | 调用实际 ChatServer:Send → Context/快照 → 模拟提供商结果 → Communication → RequestGoal → 两种完成场景及缺科技场景；不是直接 RequestPlan 测试；UI、JSON传输和提供商仍为模拟 |
| Python后台/本地HTTP | 17个测试通过 | 严格目标/schema、具体诊断、安全日志、非法结果零下发、合法目标传输/去重和拒绝模型动作步骤；提供商为模拟 |
| 真实模型请求 | 未执行 | 本地没有用户配置密钥；运行 check_goal_live.py 明确返回 NOT RUN，没有请求提供商 |
| 真实 DST 聊天/引擎 | 未执行 | 当前环境没有 DST 客户端，必须在用户实际环境按4组验收 |

`tests/v0120_foundation_results.txt`、`tests/v0120_ai_results.txt` 保存上述模拟结果。提示词示例、手工目标或模拟提供商返回值都**不是**真实自然语言链已经通过的证据。

`external/check_goal_live.py` 为可选本机单次真实提供商解析检查，使用原本地配置，不输出密钥，不操作游戏，也不替代实际聊天入口验收。正常直接进行必要测试组1即可，未安排重复密钥配置、创建/存档、普通跟随和已通过UI的全面测试。
