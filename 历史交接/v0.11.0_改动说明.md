# v0.11.0 改动说明

以当前 v0.10.0 包为基线修复，保留已验证的密钥、聊天入口、朋友创建/存档/跨区与普通跟随等待实现。无需重复这些功能的全面测试。

## 对应本次10项反馈

| 1 找不到草没有回应、范围小 | 找不到目标明确报告物品和实际半径；反馈同时进入聊天、游戏公告及头顶说话。最小/默认半径32，保留起点与朋友双重边界。工作执行异常也释放任务并报告，不静默挂住。 |

| 3 组合指令只拿1块石头 | 新增有界统一步骤计划，支持多资源收集与后续交付。“一些”默认每种3个；金矿选择继续依据真实掉落表。进度仍按实际库存，不按成功回调计数。 |
| 4 一个个给予太慢 | 新给予动作调用原版 trader 接收逻辑，每次转交当前叠中所需、且此刻能够接收的数量；不同叠/不同物品分别给予。不会全包上交。 |
| 5 不知道手里有什么 | 库存快照包含装备、鼠标持有与溢出背包，标注装备位置。明确手持问题直接读当前手持装备，避免模型漏掉。 |
| 6 砍一棵树变成捡1木头 | 新 tree 目标计实际砍倒棵数，检查掉落后结束；与 collect/log 的库存数量目标分开。 |
| 7 不理解拿起斧子 | 新 equip 步骤，真实检查并装备已有物品。普通“斧子/鹤嘴锄”可选持有的适用同类工具，不要求一定是基础斧/镐；不会免费造工具。 |
| 8 要石砖应找石头、靠近科技、制作、交付 | craft prepare=true 在同一工作控制下备齐一级基础材料、找到可使用的现有科技并走近、再次检查实际制作条件，再用原版 BUILD 消耗与产出、正常解锁。ensure=true 把已有成品计入“我要”的目标，仅制作缺额；明确“用现有材料做”仍保留材料不足失败原因。 |
| 9 不应隔空知道玩家背包满 | 选交付目标与走路阶段不读取玩家容量/物品数。进入玩家身边的给予动作执行点后，检查当前接收能力并尝试接收；失败保留物品并报告。部分交付后容量不足会再次尝试并停止剩余交付；单项库存不足则汇报实际交付量并继续计划里其他物品。 |
| 10 不认识炖肉汤 | 截图里实际快照已经有 bonestew；补充“炖肉汤/肉汤”别名，强化实际名称、prefab 与供应快照联合识别提示。通用快照包含朋友持有物品名称及装备，避免只按食物/背包槽位判断已知物品。 |

## 执行与接口

游戏内统一处理条件检查、选目标、移动、执行、读真实结果、更新进度和下一步。AI只提交意图计划；不会逐击或逐次拾取调用模型。

- `Request(kind,item,quantity,owner)` 保留单工作接口。
- `RequestPlan(entries,owner)` 新增1至12步计划；step 为 `kind/item/quantity`，craft 可有 `prepare` 和 `ensure` 布尔标志。
- `Status(task_id)` 提供当前步骤、计划、实际数量、暂停状态或最后结果/汇总；plan_result 逐步列出实际数量，并以全部步骤是否完成判断整体成功；`Cancel(restore)` 令全部旧动作与剩余步骤失效。
- 工作和补状态仍互斥。连续挥动时如确有可用补给需要处理，会停止连击，让原补状态逻辑接管；没有可用补给不会无故拖慢每一击。恢复后重新检查目标、工具与材料。
- 成功、失败或停止只恢复原有跟随/等待安排；没有新增瞬移。等待任务结束仍沿用原本的返回等待点流程，返回失败就在当前位置等待。
- 每阶段有有限时限；单目标仍最多两次无进展/无法到达失败，工具更换有上限。真实库存与材料/产出审计继续保留。
